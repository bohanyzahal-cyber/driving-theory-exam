# session-gateway — שער סקרים מאחד + מאגר השאלות הפרטי

Worker עם שלושה תפקידים (DESIGN_2026-09-21 §3.4, §11 ו‑§13):

1. **מאחד את סקרי הנבחנים:** קריאה אחת ל‑Apps Script לכל סשן, כמה נבחנים שלא יסקרו —
   ומאז r31.2 גם **רק כשקרה משהו**: שרשרת חדשה מקבלת עותק טרי (2 שניות), שרשרת שמחדשת את
   עצמה מקבלת עותק עד 20 שניות, וכל כתיבה דוחפת. במקום ~480 הרצות לדקה ל‑40 נבחנים — **3
   הרצות לדקה** לכיתה שקטה.
2. **מגיש את טקסטי השאלות.** הבנק **אינו ציבורי**: הוא נכס סטטי פרטי של ה‑Worker
   (`run_worker_first`), וכל מכשיר מקבל **רק את המזהים שהאישור החתום שלו נוקב בהם**.
3. **מצייר את לוח הבוחן** (r31 + r32): הלוח מחזיק בקשה אחת פתוחה כאן במקום לקרוא ל‑Apps
   Script כל 5 שניות; כשטביעת האצבע של הסשן זזה התשובה חוזרת מיד — ומאז r32 היא גם **נושאת
   את השורות והתוצאות עצמן** (`session`), כך שלכל שינוי יש **סיבוב אחד** לגוגל במקום שניים.

## נקודות קצה

| נתיב | מי מורשה | תשובה |
|---|---|---|
| `GET /` | — | `{status:'ok', service:'session-gateway', build:'…', bank:'<manifest.build>'}` |
| `GET /v1/poll?kind=approval&sessionCode=ABC12345&idNumber=…&examineeToken=…` | — | בדיוק כמו `checkApproval` בשרת (כולל `approval:rejected`/`cancelled` כשזו השורה החדשה ביותר ואין רישום חי — 21/09 ערב) |
| `GET /v1/poll?kind=status&…` | — | בדיוק כמו `getExamStatus` בשרת |
| `GET /v1/poll?…&wait=25&fp=<טביעת האצבע האחרונה>` | — | **סקר ארוך:** אותה תשובה, אבל הבקשה מוחזקת עד שהתשובה משתנה |
| `GET /v1/session/watch?grant=…&sessionCode=ABC12345[&wait=25&fp=…]` | scope `examiner` בלבד | **הצפייה של הלוח:** `{"status":"ok","fp":"s:…","held":<ms>,"rows":<n>,"at":<ms>[,"stale":true][,"session":{"rows":[…],"results":[…]}]}` — נענית ברגע שמשהו בסשן השתנה, ומאז r32 נושאת את הנתונים |
| `GET /v1/bank?grant=…` | scope `exam`/`practice` | המזהים שב‑grant, בכל 7 השפות |
| `GET /v1/bank?grant=…&ids=1,2,3[&langs=he,en]` | scope `examiner` | עד 60 מזהים; `langs` מסנן שפות |
| `GET /v1/bank/full?grant=…&lang=he` | scope `examiner` בלבד | הבנק המלא של השפה, כזרם |
| `POST /v1/invalidate?grant=…&sessionCode=ABC12345` | scope `examiner` בלבד | `{"status":"ok"}` — מוחק את ה‑snapshot של הסשן |
| `POST /v1/invalidate?grant=…&sessionCode=…&idNumber=…&status=approved` <br>`[&examMinutes=50&extraMinutes=0&audio=on]` | scope `examiner` בלבד | `{"status":"ok","patched":true}` — כותב את ההחלטה **לתוך** ה‑snapshot |
| `POST /v1/invalidate?sessionCode=…&idNumber=…&examineeToken=…` <br>(**בלי** `grant` ו**בלי** `status`) | הנבחן עצמו, לפי הטוקן שלו | `{"status":"ok","dropped":true\|false}` — דחיפה אחרי הגשה/"סיים במכשיר"; **מוחקת בלבד, לעולם לא כותבת** |

תשובת הבנק: `{"status":"ok","build":"…","questions":[…],"missing":[…]}` — `questions` הוא
תוכן `assets/q/<id>.json` **כמות שהוא** (ללא `JSON.parse` בנתיב החם), לפי סדר המזהים;
`missing` הם מזהים בלי קובץ. `Cache-Control: no-store` בכל התשובות.

תשובות הסקר זהות לאלו של השרת — הלקוח מחליף כתובת בלבד, לא לוגיקה. שדה נוסף אחד: `stale:true`
כשהתשובה חושבה מעותק ישן (עד 60 שניות) כי ה‑upstream נכשל. כשאין שום עותק:
`{status:'error', code:'upstream_unavailable', retryable:true}` ב‑HTTP 200 — הלקוח מאט,
**לא** נופל חזרה לסקר ישיר (אחרת סערת הבקשות חוזרת) — ומאז 21/09 ערב אין מסלול ישיר בכלל: ה‑Worker הוא הדרך היחידה, וכשהוא לא עונה הדף מנסה שוב עם backoff.

הטוקן של הנבחן לא עוזב את Apps Script: ה‑snapshot מחזיק `tokenHash` (SHA‑256), וה‑Worker
מגבב את מה שהלקוח שלח ומשווה.

### סקר ארוך (long polling) — `wait` + `fp`

הלקוח סוקר כל 2–6 שניות. לכל החשבון יש תקרה קשיחה של 100,000 בקשות ליום (כל ה‑Workers יחד),
ובוקר בחינות כבד כבר נגע ב‑~130k. לכן כל תשובת סקר נושאת **טביעת אצבע** (`fp`), והלקוח יכול
לבקש שהבקשה **תוחזק** עד שהתשובה באמת תשתנה:

```
GET /v1/poll?kind=approval&sessionCode=ABC12345&idNumber=…&wait=25&fp=a%3Awaiting%3Aoff%3A-
```

* `wait` — שניות שלמות, נצמד ל‑**1–25**. כל ערך אחר (0, 2.5, `abc`, ריק, שלילי) = תשובה מיידית,
  בדיוק כמו היום.
* `fp` — טביעת האצבע האחרונה שהלקוח קיבל. **חייב קידוד** (`encodeURIComponent`) — יש בה נקודתיים.
* הבקשה מוחזקת **כל עוד** ה‑fp הנוכחי זהה לזה שנשלח, וחוזרת ברגע שהוא שונה — או בתום `wait`
  (ואז עם אותה תשובה ואותו fp). צריך **גם** `wait` **וגם** `fp`; בלי אחד מהם — התנהגות היום.

הרווח כפול: פי 4–5 פחות בקשות, **וגם** החלטת בוחן על המסך תוך ~שנייה, כי כבר אין "עוד סקר
אחד" שמתווסף לכתיבה של Google. ההחזקה קצרה בכוונה (≤25 שניות) והלולאה טיפשה בכוונה: המסלול
החינמי נותן 10ms CPU לבקשה, וזה מה שפוסל WebSocket או SSE שמוחזק 40 דקות.

**הפורמט של `fp`** — מחרוזת קצרה (עד ~40 תווים) שמשתנה **בדיוק** כשהתשובה של הנבחן הזה
משתנה, ומשום דבר אחר (לא גיל ה‑snapshot, לא שורה של נבחן אחר). היא אטומה ללקוח, שרק מחזיר
אותה כמות שהיא:

| התשובה | `fp` |
|---|---|
| `kind=approval` | `a:<approval>:<on\|off>:<examMinutes או ->` — למשל `a:approved:on:50`, `a:waiting:off:-` |
| `kind=status` | `s:<examStatus>:<extraMinutes>` — למשל `s:in_exam:7` |
| אין שורה לת.ז. | `a:none` / `s:none` |
| טוקן לא תואם | `a:tok` / `s:tok` |
| `upstream_unavailable` | `x:up` |
| 400 (בקשה שגויה) | `x:kind` / `x:sess` / `x:id` |

תשובת `stale:true` נושאת את ה‑fp של התשובה **שבתוכה**, כדי שה‑fp של הלקוח לא יקפוץ רק מפני
ש‑Apps Script נפל לרגע.

**מה אף פעם לא מוחזק** (חוזר מיד, כדי שהלקוח יאט או יפסיק): `upstream_unavailable`, כל תשובת
`stale:true`, `examineeTokenError`, וכל 400. **"אין שורה" דווקא כן מוחזק** — זו בדיוק ההמתנה
שרוצים כשנבחן נרשם באותו רגע.

**תקציב אחד לכל הבקשה (תיקון 22/09).** `wait` הוא התקציב של **הבקשה כולה**, נמדד מרגע
שהגיעה — לא של ההחזקה בלבד. עד התיקון ה"מבט הראשון" לא היה חסום: בקשה שהצטרפה לקריאה
שגוגל לקח עליה 20 שניות התחילה את ההחזקה שלה באיחור של 20 שניות וענתה אחרי **45 שניות**,
מעבר ל‑deadline של הלקוח (40 שניות), שספר אותה ככשל תקשורת (ארבע בקשות כאלה ב‑tail אחד
של 24 דקות). מעכשיו:

| | |
|---|---|
| תקרה קשיחה | `wait` + שנייה אחת של grace — **גג 26 שניות** ל‑`wait=25`, מבט ראשון והחזקה יחד |
| בקשה בלי `wait` | המבט הראשון חסום ב‑`FIRST_LOOK_MAX_MS` (20 שניות) + grace, ואז תשובה מהעותק שיש (`stale:true`) — במקום להיתקע עד `UPSTREAM_TIMEOUT_MS` |
| כשהתקציב נגמר | עונים מהעותק הטוב ביותר שביד (זיכרון עד 60 שנ׳ → `stale` ב‑Cache) מסומן `stale:true`, ואם אין — `upstream_unavailable`. שניהם **לא מוחזקים** |
| הקריאה עצמה | **נזנחת, לא מבוטלת** — היא מאוחדת, ומי שישאל אחריה ייענה ממנה (`ctx.waitUntil`) |
| `held` | נמדד מתחילת הבקשה, ולכן זה בדיוק מה שהלקוח רואה בשעון שלו |

**למה כל המתנה מרוצה מול טיימר (תיקון 22/09).** 15 מתוך 74 בקשות ב‑tail חזרו **HTTP 500**
עם `"exception"` ו‑«the Workers runtime canceled this request because it detected that your
Worker's code had hung» — 2–3 ms wall time, 0 CPU. זו זיהוי‑התקיעה של Cloudflare, והוא יורה
על בקשה שממתינה ל‑promise ש**בקשה אחרת** יצרה (הקריאה המאוחדת שלנו, שנשארת חיה רק דרך ה‑
`waitUntil` של אותה בקשה אחרת) **בלי שום I/O או טיימר משלה**. לכן כל הצטרפות ל‑promise
משותף עוברת ב‑`within(ms, promise)`, שמרכיב טיימר של הבקשה הנוכחית ומשחרר אותו ברגע שההכרעה
נפלה. מאותה סיבה מפתח ה‑HMAC נשמר כ**מפתח**, לא כ‑promise: בקשה קרה מייבאת לעצמה.

**מה קורה בזמן ההחזקה.** כל שנייה (או ברגע שמשהו מעיר את הבקשה) מחושבת התשובה מחדש: הזיכרון
של האיזולייט קודם, `caches.default` **בכל סבב** — כדי שטלאי שאיזולייט אחר כתב ב‑`/v1/invalidate`
ייראה תוך סבב אחד — וקריאה ל‑Apps Script רק כשהעותק חצה את **קצב הביטחון** (למטה), ואז
**מאוחדת** לכל הממתינים של הסשן. בנוסף, `patchSnapshot`, `dropSnapshot` וכל קריאת upstream
שהסתיימה **מעירות** את כל הבקשות המוחזקות של אותו סשן, ולכן נדנוד של בוחן חוזר לבקשה שמוחזקת
באותו איזולייט תוך ~0 מילישניות. תקרה קשיחה של 26 חישובים לבקשה שומרת על תקציב ה‑CPU גם
כשמעירים אותה הרבה.

### קוראים לגוגל רק כשקרה משהו (r31.2, 22/09 11:15 — KNOWN_ISSUES #35)

**הממצא:** שלב מסירת התשובה של גוגל נתקע 25–60 שניות **לפרויקטים שלנו**, בזמן שפרויקט סרק
באותו חשבון לא נפגע. הדבר הכי תובעני ששלחנו לגוגל היה **הקריאה הזאת עצמה** — `sessionSnapshot`
כל ~2 שניות לכל סשן: 30 לדקה לכיתה במבחן, ו‑10 לדקה ללוח בוחן שאף אחד לא מסתכל עליו. והיא
לא חייבת להיות שעון בכלל: **כל כתיבה של לקוח כבר מודיעה על עצמה** (טלאי/מחיקה של הבוחן;
דחיפת הנבחן אחרי הגשה, "סיים במכשיר", הרשמה, פסילה, ביטול פסילה ואזהרה).

| מתי ה‑Worker קורא לגוגל | |
|---|---|
| (א) **שרשרת חדשה** — בקשה **בלי** `fp` (טעינת דף, הסקר הראשון אחרי הרשמה, לוח שנפתח) | חלון `FRESH_MS` = **2 שניות**, בדיוק כמו קודם |
| (ב) **נדנוד מחק את ה‑snapshot** | קריאה אחת מאוחדת, בתקציב `REREAD_GAP_MS` (2 שניות לסשן) |
| (ג) **שורה חסרה** (`provisional`) | קריאה כפויה אחת לפני שאומרים "לא נמצא רישום", כמו קודם |
| (ד) **קצב ביטחון** `HELD_REREAD_MS` = **20 שניות** | בקשה **עם** `fp` (חימוש מחדש של שרשרת, וכל סבב של החזקה) מקבלת עותק עד 20 שניות — הלקוח כבר מחזיק בדיוק את המצב הזה, ורק שינוי מעניין אותו |

`HELD_REREAD_MS` **חייב** להישאר קטן מ‑`STALE_MS` (60 שניות), אחרת שרשרת מוחזקת הייתה מתיישנת
לפני שרעננה — הקובץ נופל בטעינה אם מישהו ישבור את זה, ויש בדיקה שמוכיחה את זה.

**למה 20 ולא 45 (12:29, אותו יום):** בקשת האישור של הבוחן ל‑Apps Script **נתקעה 30 שניות
ונכשלה בדף** — ולכן הדף לא קיבל `ok` ולא שלח נדנוד כלל, והנבחן ראה את האישור רק כשהקצב
הפסיבי הגיע. דף הבוחן שולח עכשיו נדנוד‑מחיקה **גם כשהבקשה נכשלת**, אבל הרצפה הפסיבית חייבת
להיות מספר שאפשר לחיות איתו כששניהם אבדו: 20 שניות = 3 קריאות לדקה לסשן מוחזק.

**מה זה נותן (נמדד ב‑`gateway.test.cjs`, שעון מדומה):** 40 נבחנים מוחזקים + לוח בוחן מוחזק,
**עשר דקות בלי שום אירוע** — **29 הרצות Apps Script** במקום ~300 (פי 10). כיתה שלמה שלא קורה
בה כלום עולה לגוגל 3 פעמים בדקה, ולא 30.

**מה זה עולה:** שינוי ש**אף אחד לא דחף** (תיקון ידני בגיליון, השלמה אוטומטית של שורה תקועה,
או החלטת בוחן שגם הכתיבה שלה וגם הנדנוד שלה נכשלו) נראה תוך עד 20 שניות במקום עד 2. כל שינוי
שמגיע מהמערכת עצמה — החלטת בוחן, הרשמה, הגשה, פסילה — מגיע **מיד**, כי מי שכתב אותו גם דחף.
לוח הבוחן ממילא מחזיק רשת ביטחון משלו (60 שניות, §13.2).

**רמז למי שקורא לוג:** `age` בשורת היומן הוא גיל העותק שענה. `age` שמטפס עד ~20,000 ואז
מתאפס = הקצב הפסיבי; `age` קטן = מישהו דחף.

**שני שדות חדשים בתשובה** — ורק למי שביקש (כלומר שלח `wait` או `fp`):

| שדה | מה |
|---|---|
| `fp` | טביעת האצבע של התשובה הזו — זה מה שמחזירים בבקשה הבאה |
| `held` | כמה מילישניות הבקשה הוחזקה בפועל (0 אם לא הוחזקה). דיאגנוסטיקה בלבד |

למי ש**לא** שלח אף אחד מהשניים התשובה זהה **בתו ובתו** לתשובת השרת, כמו קודם — כך לקוח ישן
ממשיך לעבוד בלי שינוי, וזה מה ש‑`tests/contracts.test.cjs` נועל. לכן: **בסקר הראשון, כשעוד
אין fp ביד, שולחים `fp=` ריק (או `wait=`)** — אחרת לא יחזור `fp` בגוף התשובה ולא יהיה מה
לשלוח בסקר הבא.

### `/v1/session/watch` — לוח הבוחן בלי טיימר (r31 §13.2), ועם הנתונים (r32 §14.1)

עד r31 לוח הבוחן קרא ל‑`examinerDashboard` כל 5 שניות — הרצת Apps Script מלאה, גם כשלא קרה
כלום — והרשמה או הגשה הופיעו בו אחרי ~20 שניות. עכשיו הלוח מחזיק **בקשה אחת** כאן ושואל
"משהו בסשן הזה השתנה?" — ומאז r32 התשובה גם **נושאת את מה שהשתנה**, כך שהלוח מצטייר בלי
סיבוב שני לגוגל:

```
GET /v1/session/watch?grant=<אישור בוחן>&sessionCode=ABC12345&wait=25&fp=s%3A9f1c0a2b7d43
→ {"status":"ok","fp":"s:1d0c4e77aa91","held":0,"rows":12,"at":1758480000123,
   "session":{"rows":[…12 שורות…],"results":[…התוצאות של הסשן…]}}
```

* **`grant` חובה — scope `examiner`** (אותו grant מ‑`bankGrant`). בלי אישור תקף: **HTTP 403**
  `{"status":"error","code":"grant_invalid"}`. `sessionCode` לא תקין → **400**.
* `wait` ו‑`fp` בדיוק כמו בסקר הארוך (1–25 שניות, כל ערך אחר = תשובה מיידית; `fp` חייב
  `encodeURIComponent` — יש בו נקודתיים). הבקשה הראשונה, בלי `fp`, נענית מיד.
* `rows` הוא **מספר** השורות (דיאגנוסטיקה, כמו ב‑r31), ו‑`at` הוא מתי נקרא ה‑snapshot.
  **`session.rows` הוא המערך עצמו** — שני שדות שונים באותה תשובה, בכוונה: דף r31 קורא רק את
  הראשון וממשיך לעבוד.
* **אין snapshot בכלל** → `{"status":"error","code":"upstream_unavailable","retryable":true,…,"fp":"x:up","held":0}`;
  עותק ישן → אותה תשובה עם `"stale":true`. שניהם **לעולם לא מוחזקים** — הלוח חוזר לרשת
  הביטחון שלו (5 שניות) עד שה‑Worker מתאושש.

**`session` — מתי הוא נשלח, ומה יש בו (r32).** שלושה תנאים, וכולם חייבים להתקיים:

| תנאי | למה |
|---|---|
| ה‑snapshot הוא **`v >= 2`** (שרת r32) | שרת r31 לא שולח לא את שדות השורה הנוספים ולא את `results`; חצי לוח גרוע מכלום, ולכן הדף נופל חזרה לקריאת `examinerDashboard` בדיוק כמו ב‑r31.3c |
| התשובה **אינה `stale`** | עותק שלא הצלחנו לרענן עלול להיות דקה מאחור; לא מציירים ממנו כיתה — הדף מפעיל את רשת הביטחון שלו |
| **הטביעה זזה**, או שהלקוח לא שלח `fp` בכלל | החזקה שפגה בלי שינוי עונה את אותה טביעה ו**בלי** `session` (אחרת כל לוח פתוח היה מקבל 5–40 KB כל 25 שניות על לא כלום). הבקשה הראשונה של שרשרת — בלי `fp` — **כן** מקבלת אותו: זו בדיוק הנקודה שבה לדף אין עדיין נתונים |

* `session.rows[i]` = השורה כמו שהשרת שלח אותה, **בלי `tokenHash`** (הטוקן לא יוצא מ‑Apps
  Script, וגם הגיבוב שלו לא יוצא מכאן). בשורה יש, נוסף לשדות r31: `name, phone, time, start,
  lang, pop, site, lic, timeExt, lastWarn, attemptsToday` ו‑`todayExams` כשיש.
* `session.results` = התוצאות של הסשן מזנב `תוצאות` (האחרונה לכל ת.ז., לא‑`בוטל`) —
  **בלי `wrongDetails`** (הבלוק הכבד; הדף קורא אותו מ‑`examinerDashboard` בלחיצה שבאמת צריכה
  אותו), **עם** `fabricated:1` כשצריך.
* **טלאי** (`/v1/invalidate` עם החלטה) שומר את `v` ואת `results` של העותק שהוא מטליא — הוא נוגע
  בשורה אחת, ולכן החזקה שמתעוררת ממנו מקבלת `session` מלא בלי שום קריאה לגוגל.
* **תאימות לשני הכיוונים:** Worker r32 מול שרת r31 → אין `session`, והטביעה **זהה בייט‑לבייט**
  ל‑r31 (ראו למטה); Worker r31 מול שרת r32 → אין `session` כי הוא לא יודע עליו; דף r31 מול
  Worker r32 → מתעלם משדה שהוא לא מכיר. אפשר לפרוס כל אחד מהשלושה לבד.

**זה לא עולה לגוגל כלום נוסף.** ה‑snapshot שהצפייה מטביעה הוא אותו snapshot שהסקרים של
הנבחנים ממילא מרעננים כל ≤2 שניות; הצפייה רוכבת עליו ועל אותן יקיצות (`patchSnapshot`,
`dropSnapshot`, קריאה שהסתיימה). 40 נבחנים מוחזקים + לוח אחד מוחזק = **הרצה אחת ל‑2 שניות**,
בדיוק כמו בלי הלוח. ההחזקה עצמה היא **אותה לולאה בדיוק** של `/v1/poll` (`holdUntilChanged`),
כולל תקרת 26 החישובים לבקשה. מאז r32 גם **הסיבוב השני נחסך**: מה שהשתנה נוסע בתשובה עצמה,
והרצת `examinerDashboard` נשארת רק לנפילה לאחור ולמה שצריך `wrongDetails`.

**טביעת האצבע של הסשן** — `s:` + 12 ההקסה הראשונות של SHA‑256 על השורות (ומאז r32 גם על
התוצאות), בסדר ה‑snapshot:

| | |
|---|---|
| מה נכנס להטבעה | לכל שורה `id \| status \| audio \| examMinutes \| extraMinutes \| warn \| fin \| ext \| dq`, מופרד ב‑`;` בין שורות |
| ומאז **r32**, כשיש תוצאות | `<השורות>#<התוצאות>` — לכל תוצאה **כל** השדות בסדר קבוע: `date, idNumber, name, phone, license, score, percent, passed, time, examiner, site, classroom, language, attempt, sent, disqualified, waLink, population, corrected, audioMode, verified, suspicious, device, fabricated` |
| מה **לא** נכנס | `snapshot.at` (זז בכל קריאה מגוגל — אחרת הלוח היה נקרא כל 2 שניות לנצח), `tokenHash` (הבוחן לא רואה אותו) ושדות השורה שנוספו ב‑r32 (`name`, `phone`, `site`…) — הם לא משתנים בלי שדה שכן נצפה |
| **בלי תוצאות** (שרת r31, מערך ריק) | הקלט הוא **השורות בלבד** — הטביעה **זהה בייט‑לבייט** ל‑r31. זה מה שמאפשר לפרוס את ה‑Worker לפני הדבקת השרת (§14.5) בלי להזיז אף טביעה: שתי גרסאות Worker שמגבבות סשן אחד בשתי דרכים = ה‑flip‑flop של 22/09 |
| סשן בלי שורות ובלי תוצאות | `s:none` — **ומוחזק**: ההרשמה הראשונה יוצרת שורה ומעירה את הצפייה |
| חסר = אפס | **רק** ב‑`warn/fin/ext/dq`: שדה שאינו קיים, `''`, `0`, `'0'` ו‑`false` מוטבעים כולם כ‑`''`. בכל שאר השדות: חסר/`null`/`''` → `''`, וכל השאר `String(value)` (כולל `true`/`false` של תוצאה) |

**למה "חסר = אפס" (22/09, מ‑`wrangler tail`):** בשלושה מקטעים של ~2 שניות, כל ~60–80 שניות,
התשובות לאותו סשן **התחלפו הלוך ושוב** בין שתי טביעות — בלי שום כתיבה, בקשות במרווח 250 ms.
באותו בוקר המערכת עברה r30→r31, ולכן חיו **בו‑זמנית שני snapshot בצורות שונות**: ישן בלי
`warn/fin/ext/dq` (מוטבע `''`) לצד חדש עם `0` (מוטבע `'0'`). `lookAtNewest` מחזיר את העותק
ש**שונה** ממה שהלקוח מחזיק — ולכן הזיכרון וה‑Cache החזירו זה את זה לסירוגין עד אינסוף.
שרת ישן מול Worker חדש מנטר פשוט פחות שדות, וממשיך להתעורר על שינוי סטטוס ועל הרשמה.

**מתי היא מחושבת:** פעם אחת, **במקום שבו ה‑snapshot נשמר** — `fetchCoalesced` (אחרי קריאה
מוצלחת) ו‑`patchSnapshot` — ונוסעת עם ה‑snapshot לתוך `caches.default` בתוך ה‑JSON (שדה
`sfp`). `caches.default` מחזיר **אובייקט חדש בכל קריאה**, ולכן בלי זה כל טיק של החזקה היה
מגבב מחדש: **7–12 ms CPU לבקשה** מוחזקת, מול תקרה של 10 ms בתוכנית החינמית (נמדד ב‑tail).
עותק שנכתב לפני r31 אינו נושא `sfp` ומגובב כרגיל.

**ומאז r32 גם לא מפרסרים (TODO 0א.6).** בקשה מוחזקת קוראת את `caches.default` **בכל טיק** —
זה הערוץ שדרכו מגיע טלאי מאיזולייט אחר — ו‑`JSON.parse` של snapshot שלם (5–40 KB, ועכשיו גם
עם התוצאות) כל שנייה היה רוב מה שהבקשה עולה. לכן `cacheWrite` חותם על ה‑Response המאוחסן גם
**כותרות**: `X-SFP` (הטביעה) ו‑`X-RAT` (מתי העותק נעשה עדכני, בשעון של ה‑Worker), ו‑
`cacheFingerprint()` קוראת **רק אותן** (`match` בלי `json()`). כשהטביעה בכותרת זהה לזו שבזיכרון —
אותו snapshot, אין מה לפרסר. רק כשהיא **שונה** נפתח הגוף. עותק שנכתב לפני r32 אינו נושא
כותרות → "לא ידוע" → קריאה מלאה, בדיוק כמו r31. בנוסף, עותק שנקרא מהמטמון כשאין כלום בזיכרון
**מאומץ לזיכרון** (עם הגיל שכבר היה לו, לא "עכשיו"), כדי שהטיק הבא ישווה כותרת בלבד.
נמדד בבדיקות: החזקה שקטה של 25 שניות = **25 `match`, 0 `json()`** (ב‑r31: ~23 פרסורים).

### `/v1/invalidate` — דחיפה אחרי החלטת בוחן

אחרי אישור/דחייה/איפוס/פסילה/הארכת זמן, דף הבוחן שולח `POST` (fire‑and‑forget, `keepalive`).
**שתי הצורות דורשות `&grant=` עם אישור בוחן חתום** (scope `examiner` — אותו grant שהדף מקבל
מ‑`bankGrant` בכניסה). בלי אישור תקף: HTTP 403 `{"status":"error","code":"grant_invalid"}`,
ושום דבר לא נמחק ולא נכתב. בלי זה כל מי שיודע קוד סשן ות.ז. של נבחן אחר היה יכול להראות
לו "נפסלת" מהטלפון — ומסך הפסילה מפסיק לסקור. שתי צורות:

**מחיקה (`?sessionCode=X` בלבד).** ה‑Worker מוחק את ה‑snapshot של הסשן מהזיכרון ומשתי רשומות
ה‑Cache (`snap`, `stale`), כך שהסקר הבא של הנבחן קורא מהשרת מיד במקום לחכות לתום חלון ה‑2
שניות. **מוגבל לקריאה חוזרת כפויה אחת לכל 2 שניות לסשן** — אותו תקציב שממנו שואב גם הרענון
האוטומטי של "שורה שחסרה ב‑snapshot", כך שסופת `invalidate` לא יכולה להכפיל את העומס על
Apps Script. התשובה תמיד `{"status":"ok"}`, גם כשהמגבלה בלמה את המחיקה.

**טלאי (`&idNumber=…&status=…`).** הנדנוד נושא את ההחלטה עצמה. ה‑Worker לוקח את ה‑snapshot
הנוכחי של הסשן (זיכרון → `snap` → `stale`), מוצא את השורה **האחרונה** של אותה ת.ז. (סדר
הגיליון הוא הישן ראשון), כותב בה `status` — ואם נמסרו ותקינים גם `examMinutes`, `extraMinutes`
ו‑`audio` — ושומר את ה‑snapshot כ**טרי** (זיכרון + `snap` + `stale`, אותו גוף). הסקר הבא של
הנבחן, **כשנייה אחרי הלחיצה**, עונה את ההחלטה **בלי שום קריאה לשרת**. התשובה:
`{"status":"ok","patched":true}`.

*למה זה לא הקדמת האמת:* דף הבוחן יורה את הנדנוד **רק אחרי** ש‑Apps Script ענה `status:'ok'`,
כלומר אחרי שהשורה כבר נכתבה בגיליון — הטלאי אינו יכול להקדים את המצב האמיתי ביותר מאותה
כתיבה מאושרת. הוא גם קצר‑חיים: העותק פג על שעון ה‑`FRESH_MS` הרגיל, והסקר שאחריו קורא את
השורה מהשרת וממילא דורס אותו. זה מה שהופך את "2–4 שניות" של DESIGN §11.8 ל‑**כשנייה**
באישור, בלי ערוץ push; הרצפה שנשארת היא הכתיבה של Google עצמה (~1 שנ').

טלאי הוא **כתיבה, לא קריאה**, ולכן אינו צורך את תקציב הקריאה החוזרת — `invalidate` רגיל מיד
אחריו עדיין מוחק. כשאין snapshot לסשן, או שאין בו שורה לאותה ת.ז. (הנבחן נרשם אחרי הצילום) —
נפילה חזרה למחיקה ותשובה `{"status":"ok","patched":false}`; הסקר של הנבחן ממילא קורא מהשרת
כשהשורה חסרה, ומוצא אותה בעצמו.

| פרמטר | חובה | ערכים |
|---|---|---|
| `sessionCode` | כן | `^[A-Z0-9]{6,8}$` — אחרת **400** |
| `idNumber` + `status` | רק לטלאי, ושניהם יחד | `status` אחד מתוך `waiting, approved, rejected, cancelled, in_exam, completed, disqualified, dq_confirmed`; `idNumber` חייב להכיל ספרות. ערך אחר → **400**. רק אחד מהשניים → מחיקה רגילה עם `patched:false` |
| `examMinutes` | לא | שלם 1–600; ערך לא תקין מתעלמים ממנו (שאר הטלאי עדיין נכתב) |
| `extraMinutes` | לא | שלם 0–600, כנ"ל |
| `audio` | לא | `on` / `off` בדיוק, כנ"ל |

### דחיפה **מהמכשיר של הנבחן** (r31, DESIGN §13.5)

עד r31 רק הבוחן דחף. הגשה ו"סיים במכשיר" הן כתיבות של **הנבחן**, ולוח הבוחן ראה אותן רק
בקריאה הבאה של ה‑Worker מגוגל (≤2 שנ׳) ואז בטיק הבא של הלוח (≤5 שנ׳). עכשיו המכשיר דוחף
בעצמו — `fetch(..., {method:'POST', keepalive:true})`, fire‑and‑forget, אחרי `submitResult`
שענה `ok` ו‑2 שניות אחרי `markFinished`:

```
POST /v1/invalidate?sessionCode=ABC12345&idNumber=012345678&examineeToken=<הטוקן>
→ {"status":"ok","dropped":true}
```

**בלי `grant` ובלי `status`** — זה מה שמפנה את הבקשה לדלת הזאת. ה‑Worker מגבב את הטוקן
(SHA‑256) ומשווה ל‑`tokenHash` של **השורה החדשה ביותר** של אותה ת.ז. ב‑snapshot הנוכחי
(זיכרון → `snap` → `stale`) — הטוקן עצמו ממילא לא עוזב את Apps Script:

| מצב | תשובה |
|---|---|
| תואם, והתקציב פנוי | `{"status":"ok","dropped":true}` — `dropSnapshot`, והסקרים והצפיות המוחזקות של הסשן מתעוררות וקוראות מיד |
| תואם, אבל היתה כבר קריאה כפויה ב‑2 השניות האחרונות | `{"status":"ok","dropped":false}` |
| **אין snapshot לסשן** | `{"status":"ok","dropped":false}` — אין מה למחוק, אין את מי להעיר, והתקציב לא נגע |
| טוקן חסר / לא תואם / השורה בלי `tokenHash` / אין שורה כזאת | **403** `{"status":"error","code":"grant_invalid"}` |
| הבקשה נושאת `status` (או `grant`) | נשפטת בדלת של הבוחן — בלי אישור תקף **403**, ושום דבר לא נכתב |

**לעולם לא טלאי.** מכשיר יכול לומר "תסתכל שוב", לעולם לא "מה לראות": רק הבוחן כותב לתוך מה
שכל הנבחנים בסשן נקראים ממנו. התקציב הוא **אותו** `mayForceReread` של הבוחן (קריאה כפויה אחת
לסשן ל‑2 שניות), כך שמכשיר שדוחף בלולאה לא יכול לקנות יותר הרצות Apps Script מבוחן אחד שלוחץ.

### האישור החתום (grant)

מחרוזת `<payload>.<sig>`: `payload` = base64url של JSON, `sig` = base64url של
HMAC‑SHA256(`GATEWAY_KEY`, `payload`). **רק Apps Script חותם** (`startExam`, `startPractice`,
`bankGrant`); ה‑Worker מאמת ב‑`crypto.subtle.verify` (השוואה בזמן קבוע) ולעולם לא סומך על
הלקוח. ה‑payload: `{"v":1,"s":"exam","ids":[14,120],"sub":"ABC12345:012345678","exp":<ms>}`.

grant לא תקין / פג תוקף / scope לא מתאים → **HTTP 403** `{"status":"error","code":"grant_invalid"}`.
אין נכסים (binding חסר או כל הקריאות נכשלו) → **HTTP 503**
`{"status":"error","code":"bank_unavailable","retryable":true}`.

```
assets/q/<id>.json        שאלה אחת, כל השפות: {"id":14,"l":{"he":{t,a,i,v?},"ru":{…},…}}
assets/bank/<lang>.json   הבנק המלא של שפה: [{id,t,a,i,v?},…] ממוין לפי id
```

**`node tools/build_bank.js` חייב לרוץ לפני כל `npx wrangler deploy`** — הוא מה שבונה את
`assets/`. התיקייה **ב‑`.gitignore`**: הטקסטים לא בריפו ולא ב‑Pages, ולכן קלון טרי (בלי
`deployment/generated/questions_<lang>.json`) **אינו יכול** לבנות אותה, ופריסה ממנו תעלה בנק ריק.

## פריסה

```bash
node tools/build_bank.js                # בונה את assets/ (מהתיקייה הראשית של הריפו)
cd cloudflare-workers/session-gateway
```

## מה צריך בצד השרת (ScriptProperties)

| Property | ערך |
|---|---|
| `GATEWAY_KEY` | הסוד שמאפשר ל‑Worker לקרוא `action=sessionSnapshot` **וגם** המפתח שבו נחתמים ה‑grants (אותו ערך כמו ב‑wrangler secret) |

אחרי פריסה כדאי גם `npx wrangler tail` לדקה של סקר אמיתי ולוודא שלוש מספרות (תיקוני 22/09):
`wallTime` של בקשה `wait=25` **לא עובר 26,000 ms**, אין `outcome":"exception"` עם
"code had hung", ו‑`cpuTime` של watch מוחזק נשאר חד‑ספרתי (r32: הטיק השקט קורא כותרת ולא
מפרסר גוף, ולכן המספר הזה אמור לרדת ולא לעלות למרות ש‑snapshot גדל). אחרי הדבקת השרת מחפשים
בו גם **`"sess":1`** — זו השורה שמוכיחה שהלוח קיבל את הנתונים מכאן, ו‑`nr` שאינו 0 בסשן עם
תוצאות.

שתי בקשות ברצף לאותו סשן צריכות להחזיר את אותה תשובה בלי הרצת Apps Script שנייה — נבדק
בגיליון ההרצות: ‏`sessionSnapshot` אחד לכל ~2 שניות של סקר, לא אחד לכל נבחן.

## יומן (`wrangler tail`)

כל תשובה של `/v1/poll` ו‑`/v1/session/watch` כותבת **שורה אחת** ב‑`console.log`:

```json
{"r":"watch","s":"R9UYX7DV","src":"memory","fp":"s:a79136fe0ef8","held":25000,
 "fl":3,"age":12840,"late":0,"up":712,"usfp":"s:a79136fe0ef8","rows":12,"nr":7}
```

| שדה | מה |
|---|---|
| `r` / `s` / `k` | הנתיב (`watch`/`poll`), קוד הסשן, ולסקר גם `k` (`approval`/`status`) |
| `src` | מאיזה עותק חושבה התשובה: `memory`, `cache`, `fetch`, `stale`, `none` |
| `fp` / `rows` / `held` | הטביעה שנענתה, כמה שורות בסשן, וכמה זמן הבקשה הוחזקה |
| `nr` | (watch, r32) כמה תוצאות יש בעותק שענה. **`nr` שתמיד 0 בסשן שיש בו מבחנים גמורים = השרת עדיין r31** — ההדבקה לא נעשתה |
| `sess` | (watch, r32) `1` = בתשובה נשלח `session` עם הנתונים. אין שדה = לא נשלח (אין שינוי / `stale` / שרת r31) |
| `fl` | כמה זמן לקח המבט הראשון (ms) — כאן רואים גוגל איטי |
| `age` | גיל העותק שענה (ms). מטפס ל‑20,000 ומתאפס = הקצב הפסיבי; קטן = מישהו דחף |
| `late` | 1 = המבט הראשון לא הספיק בתקציב והתשובה היא מעותק ישן |
| `up` / `usfp` | כמה זמן לקחה הקריאה האחרונה מגוגל לסשן הזה, ואיזו טביעה היא הולידה |

**`fp` שונה מ‑`usfp` פירושו שעותק בצורה אחרת חי לצד מה שגוגל נתן לאחרונה** — זו בדיוק
הקפיצה של 22/09, ובשורה אחת רואים אותה.

## תקציב

100k בקשות/יום **לכל החשבון** — משותף עם ה‑TTS, ה‑proxy לתמונות ו‑worker הדו"חות. מעל
התקציב Cloudflare מחזיר 5xx (שגיאה 1027 עד חצות UTC), והלקוח ממשיך לנסות את ה‑Worker עם backoff (אין נפילה לסקר ישיר). עם
הסקר הארוך הצפי ~100 בקשות לנבחן ביום.

מאז r31.2 (קריאה רק כשקרה משהו) כיתה שלמה בלי אירועים עולה **3 הרצות Apps Script לדקה**
במקום 30 — פי 10 פחות מול גוגל; מספר הבקשות ל‑Cloudflare לא השתנה.

הצפייה של הלוח (r31) מוסיפה **בקשה אחת ל‑25 שניות לכל בוחן פתוח** — ~145 ליום לבוחן, כלומר
רעש ברמת הרצפה; בצד של Apps Script היא **מורידה** הרצות (הלוח נקרא רק כשיש שינוי, במקום 720
לשעה). r32 לא משנה את **מספר** הבקשות: הוא מחליף את הסיבוב השני לגוגל (`examinerDashboard`)
בשדה `session` בתשובה שממילא נשלחת. מה שכן גדל הוא ה**בתים** — 5–40 KB, אבל **רק בתשובה
שנושאת שינוי**; החזקה שקטה שפגה נשארת בת מאות בתים.

בלי הסקר הארוך: בוקר בחינות של 40 נבחנים ≈ 18k בקשות; שלושה אתרים ≈ 55k (טעינת הבנק היא
בקשה אחת למכשיר לכל מבחן, לא לכל שאלה). **עם** הסקר הארוך הסקרים עצמם — שהם כמעט כל הנפח —
יורדים פי ~4–5 (בקשה אחת ל‑25 שניות במקום אחת ל‑2–6), כלומר אותו בוקר ≈ 5k, ושלושה אתרים
נשארים הרבה מתחת לתקרה. זה מה שנותן מקום ל‑400 נבחנים ביום בלי לשלם.
