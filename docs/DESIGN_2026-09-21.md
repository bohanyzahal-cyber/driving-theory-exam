## 1. עקרונות

- **כל טקסט שאלה סטטי; השרת מחזיק רק אינדקס מזהים ומפתח תשובות.** אין Drive, אין מאגרים במטמון, אין חימום, אין lease.
- **מכשיר אחד = לכל היותר בקשה חיה אחת לכל לולאה; הסקר של הנבחנים לא מגיע ל-Apps Script אלא ל-Worker שמאחד אותו** (בקשה אחת לסשן כל 3 שנ' במקום אחת לנבחן כל 5 שנ').
- **אף קריאה מלאה של גיליון שגדל לנצח בנתיב חם:** ארכוב לילי של `מבחנים` ו-`תוצאות` כמו `ממתינים`; קוראי היסטוריה מאחדים חי+ארכיון בעמודות הנחוצות בלבד.
- **כתיבת סטטוס אחת:** כל שינוי סטטוס ב-`ממתינים` עובר דרך פונקציה אחת שגם מבטלת את ה-snapshot.
- **הלקוח מניח שהשרת עלול לענות 404/HTML גם כשהכתיבה הצליחה** (ה-302 נשלח אחרי ההרצה). תשובה כזו = "לא ידוע", לעולם לא "נכשל", ולעולם לא "גרסה חדשה" ולא "טוקן פג".
- **פריסה = בדיקות + אימות חי + רישום; אף פעם לא ב-48 השעות שלפני בחינה ולא בבוקרה.**
- **מבנה:** שרת מפוצל למודולים ב-`server/src/` ומורכב לקובץ אחד להדבקה (`external_exam_apps_script.js` = קובץ **מיוצר**); לקוח עם שכבת תקשורת אחת משותפת (`shared/transport.js`); בדיקות = שערי רגרסיה.

## 3. הארכיטקטורה

### 3.1 בנק השאלות הסטטי

- **מקור אמת:** `deployment/generated/questions_<lang>.json` (7 קבצים, == Drive, == שרשרת המקור). תיקון נתונים: id 120 עם `imageUrl:"realistic_visual_road_demo"` → ריק (35 שורות, 7 שפות).
- **בנייה:** `node tools/build_bank.js` →
  - `bank/<lang>.json`: מערך ממוין לפי id, **id ייחודי**: `{id, t, a:[…], i:'TQ_PIC_….jpg'|''}` + `v:{<license>:{t?,a?}}` רק ל-5+4 המזהים בעברית שנוסחם שונה בין שורות דרגה (1276, 829, 124, 126, 621…). בלי `ci`, בלי קטגוריה (השרת מחזיר את הנושא לכל שאלה שנבחרה). 446–696KB, gzip 140–188KB לשפה. **מחויב לריפו הציבורי.**
  - `bank/manifest.json`: `{build, langs:{<lang>:{sha, count, bytes}}}` — ה-sha משמש ל-cache-busting (`bank/he.json?v=<sha>`).
  - `deployment/question_index.json` → מוזרק בבנייה לקובץ השרת כ-`var QUESTION_INDEX`: לכל id: `{c:{<license>:<topic>}, l:<bitmask שפות זמינות>, img:0|1}`. ה-topic הוא אחד מחמשת נושאי ה-blueprint אחרי `classifyCategoryServer`; הדרגות לפי `filterByLicenseServer` (כולל 'זכות קדימה' לכל הדרגות וכלל דרגה '1'). איחוד על פני השפות + מסכת זמינות (ru בלי 907; en +6 ו-14 ב-C1). **שער:** לכל שפה×דרגה, סט המזהים מהאינדקס == סט המזהים של `filterByLicenseServer`+dedupe על ה-JSON.
- **לקוח (`BankStore`, משותף לנבחן/תלמיד/בוחן/find_image):** `load(lang)` (fetch עם `?v=sha`, Cache API דרך ה-SW, זיכרון), `get(id, lang, license)` (מיישם variant). הנבחן טוען את שפת הבחינה + עברית בזמן ההרשמה (הרבה לפני "התחל"), ושאר השפות ברקע בזמן ההמתנה. החלפת שפה = מקומית.

### 3.2 התחלת מבחן = קריאה אחת: `startExam` (POST, טוקן נבחן)

1. אימות טוקן ומצב (`approved`/`in_exam`) מתוך snapshot הסשן.
2. אידמפוטנטיות: `qmap_<session>_<id>` ב-CacheService (3 שעות) — ניסיון חוזר מקבל בדיוק את אותה מפה. אם אין במטמון: סריקת עמודות A–B של `מבחנים` (חי) ואם נמצאה שורה `in_exam` של אותו ניסיון — קריאת עמודה C של השורה ההיא.
3. בחירת 30 מזהים מה-`QUESTION_INDEX` לפי ה-blueprint של הדרגה ושפת הבחינה; לכל שאלה `shuffleOrder` (אקראי בשרת), `correctShuffledIdx` ממפתח שפת הרישום, נושא.
4. `appendRow` ל-`מבחנים` (אותן 6 עמודות — המפה JSON כמו היום, כדי שהניקוד לא ישתנה).
5. `approved → in_exam` + זמן התחלה, דרך כותב הסטטוס היחיד.
6. תשובה: `{status:'ok', build, examMinutes, extraMinutes, audioMode, questions:[{id, order:[…], topic}]}`.
- **עלות:** 0 Drive, 0 מאגרים; 1 snapshot (0–2 RT), 1 append, 2 setValue, flush. יעד ≤ 3 שנ' כולל הזנקה.
- מוסרים: `getExamQuestions`, `registerExamQuestions` (4 ניסיונות ללא אידמפוטנטיות), `markExamStarted` (נשאר רק כ-no-op אידמפוטנטי ללקוח ישן במשך גרסה אחת), `issued_qs_*`, `getQuestionsByIds` עם טקסטים.
- **תרגול (`startPractice`, GET, student/standalone):** אותה בחירה; מחזיר `{id, topic, ci:{he:…,ru:…,…}}` (ci מקודד XOR כמו היום, לכל 7 השפות) → החלפת שפה בתרגול מקומית לגמרי. `mode=category|exam|ids` (ids = חזרה מרווחת: הלקוח שולח את המזהים שלו, עד 50).

### 3.3 הגשה: `submitResult` (POST) — הלקוח שולח את מה שהוצג, השרת מנקד

- `answers[i] = {qIdx, selected, langAtAnswer, q:<טקסט השאלה כפי שהוצג>, a:[<4 התשובות בסדר שהוצג>]}`. הטקסטים משמשים **רק** לתעודה (`פירוט שגויות`, וואטסאפ); הניקוד — אך ורק ממפת `מבחנים` + `ANSWER_KEY_BY_LANG` לפי `langAtAnswer` (ללא שינוי). מוסר: `questionMetaForLanguage`/הבנקים מהשרת.
- **תיקוני נכונות (נספח ה'):** S1 מפה ריקה/קצרה (<25) → סירוב ברישום וסירוב לנקד; S2 `selected` null/''/לא-מספר/שלילי = לא נענתה; S4 ערך מהלקוח ל-`correctShuffledIdx` לא נאמן יותר (ערך לא מאומת = לא מאומת, ולעולם לא "עבר מאומת"); S7 סינון `בוטל` ב-correctToPass/commanderCorrectResult/submitWrongAnswersBulk; S8 סף תרגול = `ceil(total*0.86)` בשני הצדדים.
- **קריאות:** טוקן (snapshot) · מפה מהמטמון (נפילה: סריקת A–B + שורה) · `תוצאות`: **קריאת זנב אחת** (מסלול supersede/כפילות/פסול/אידמפוטנטיות מאותו snapshot; שורות ישנות מ-30 יום אינן רלוונטיות להגשה) · `countAttempts`: עמודות B,E,H של חי+ארכיון · append · `markPendingCompleted`. יעד: ≤ 7 RT, < 1.5MB.
- תשובה ל-404/HTML: הלקוח מסמן "לא ידוע" ושולח שוב; השרת אידמפוטנטי (session+id+ציון+זמן) — כמו היום.

### 3.4 סקר הנבחנים דרך Worker מאחד (`cloudflare-workers/session-gateway/`)

- `GET /v1/poll?kind=approval|status&sessionCode&idNumber&examineeToken` → **אותו JSON בדיוק** כמו `checkApproval`/`getExamStatus` היום (הלקוח מחליף כתובת, לא לוגיקה).
- upstream: `GET <API>?action=sessionSnapshot&sessionCode=X&gatewayKey=<secret>&origin=gateway` → `{status:'ok', at, rows:[{id, status, tokenHash, audio, examMinutes, extraMinutes}]}` (הטוקן לא עוזב את Apps Script; ה-Worker משווה SHA-256).
- איחוד: `caches.default` לפי סשן, TTL 3 שנ' + מפת in-flight בזיכרון → **הרצה אחת לסשן כל 3 שנ'** יהיו כמה נבחנים שיהיו. עותק "ישן" (60 שנ') מוגש עם `stale:true` כש-upstream נכשל.
- כשלים: upstream לא-JSON/HTTP-שגיאה → `{status:'error', code:'upstream_unavailable', retryable:true}` (HTTP 200) → הלקוח מאט (backoff) אבל **לא** נופל חזרה לישיר (אחרת הסערה חוזרת). נפילה לישיר רק כשה-Worker עצמו לא עונה (5xx/timeout/רשת) 3 פעמים רצופות, ל-5 דקות.
- מתג כיבוי בלי דחיפת Pages: `getSessionInfo` מחזיר `gateway:{url}` מ-ScriptProperty `GATEWAY_URL` (ריק = ישיר).
- תקציב חינם: 100k בקשות/יום לחשבון (משותף עם TTS/תמונות/דו"חות): 40 נבחנים × (12/דקה × 10 דק' המתנה + 7.5/דקה × 45 דק' מבחן) ≈ 18k לאתר-בוקר; שלושה אתרים ≈ 55k. מעל התקציב ה-Worker מחזיר 5xx → נפילה לישיר.
- CORS: מקור Pages בלבד. פריסה: `npx wrangler deploy` + `wrangler secret put GATEWAY_KEY` (יוסי).

## 11. חלופה T — הבנק לא ציבורי: הטקסטים מוגשים מה-Worker לפי אישור חתום (21/09/2026 ערב, הודעות 19–20 של יוסי)

**ההחלטה (הודעה 19):** הטקסטים לא יושבים בריפו ולא ב-Pages. ה-Worker (`session-gateway`) מחזיק אותם כנכסים סטטיים פרטיים ומגיש לכל מכשיר **רק את השאלות שהונפקו לו** (30 במבחן, עד 30 בתרגול), בכל 7 השפות, לפי אישור חתום (HMAC עם `GATEWAY_KEY`) ש-`startExam`/`startPractice` מחזירים. כלי הבוחן (חיפוש תמונה, "שאלות שגויות" במפקד) מקבלים אישור בוחן מהשרת ומושכים טקסטים מאותו Worker. **הודעה 20:** בוחן/מורה חוזרים לרענון אוטומטי (החלטה 4 מתהפכת); מרווחי הסקר מתקצרים; אין "יום ניסיון" — פורסים היום ובודקים הכל היום.

זה החוזה למימוש. כל סוכן עובד לפי הסעיף שלו; ממשקים בין חבילות = הצורות המדויקות שלמטה.

### 11.1 איפה הטקסטים יושבים

`node tools/build_bank.js` כותב ל-**`cloudflare-workers/session-gateway/assets/`** (לא בגיט — `.gitignore`), ו-`npx wrangler deploy` מעלה את התיקייה כ-Workers Static Assets עם `run_worker_first: true` (הנכסים לא נגישים ישירות; רק ה-Worker קורא אותם דרך `env.ASSETS.fetch`):

| קובץ | תוכן | למי |
|---|---|---|
| `assets/q/<id>.json` | שאלה אחת, כל השפות: `{"id":14,"l":{"he":{"t":"…","a":["…","…","…","…"],"i":"TQ_PIC_x.jpg" או "","v":{"D":{"t":"…","a":[…]}} (אופציונלי)},"ru":{…},…}}` — שפה שאין בה את המזהה פשוט חסרה | נבחן/תלמיד (`/v1/bank`) |
| `assets/bank/<lang>.json` | הבנק המלא של שפה, אותה צורה כמו היום: `[{id,t,a,i,v?},…]` ממוין לפי id | בוחן (`/v1/bank/full`) |
| `assets/manifest.json` | `{build, generatedAt, questions:<מספר מזהים>, langs:{<lang>:{sha,count,bytes}}}` | בריאות ה-Worker |

`deployment/question_index.json` (אינדקס בלי טקסטים) נשאר מחויב בגיט ומוזרק לקובץ השרת כמו היום. `bank/` בשורש הריפו **נמחק** מהעץ ומההיסטוריה המקומית (הקומיטים לא נדחפו). ה-Worker קורא כל `q/<id>.json` בזמן בקשה (ללא JSON.parse — שרשור טקסט; מגבלת CPU של 10ms לבקשה בתוכנית החינמית) ומגיש `bank/<lang>.json` כזרם. הבדיקות קוראות את הבנק מתיקיית ה-assets.

### 11.2 האישור החתום (grant)

מחרוזת `<payload>.<sig>`: `payload` = base64url (בלי `=`) של JSON; `sig` = base64url של HMAC-SHA256(`GATEWAY_KEY`, `payload`). השרת חותם (`Utilities.computeHmacSha256Signature`, כמו `handleGetResultUploadToken`); ה-Worker מאמת (`crypto.subtle.verify`, השוואה בזמן קבוע), ולעולם לא הלקוח.

```json
{"v":1,"s":"exam","ids":[14,120],"sub":"ABC12345:012345678","exp":1758480000000}
```

| scope `s` | `ids` | `sub` | `exp` | מונפק על ידי |
|---|---|---|---|---|
| `exam` | 30 המזהים של המבחן | `<sessionCode>:<ת.ז. מנורמלת>` | הנפקה + 4 שעות (מבחן + הארכות + רענונים; קוד סשן חי 8 שעות) | `startExam` (גם בניסיון חוזר — אישור חדש לאותם מזהים) |

**שרת (`server/src/20_auth.js`):** `gatewayKey()` (מקום אחד לקריאת ה-Property; `requireGatewayKey` משתמש בו), `signBankGrant(payloadObj)`, `bankGrantFor(scope, ids, sub)` → `{url: gatewayUrl(), grant, exp}` או `null` כשחסר `GATEWAY_KEY` או `GATEWAY_URL`. `startExam`/`startPractice` בודקים זאת **לפני כל כתיבה** ועונים `{status:'error', code:'bank_not_configured', message:'מאגר השאלות אינו מוגדר בשרת — פנה למנהל המערכת'}` כשחסר. `health` מחזיר `gateway:{url:true|false, key:true|false}`.

### 11.3 ה-Worker (`cloudflare-workers/session-gateway/`)

`wrangler.jsonc` (מחליף את `wrangler.toml`): `assets:{directory:"./assets", binding:"ASSETS", run_worker_first:true}`, `vars.API_URL`, `compatibility_date` עדכני. הסוד `GATEWAY_KEY` נשאר `wrangler secret`.

| נתיב | scope | תשובה |
|---|---|---|
| `GET /v1/bank?grant=…` | `exam`/`practice`: המזהים מה-grant · `examiner`: `&ids=1,2,3` (≤ 60) ואופציונלית `&langs=he,en` | `{"status":"ok","build":"<manifest.build>","questions":[<תוכן q/<id>.json כמות שהוא>,…],"missing":[<מזהים בלי קובץ>]}` |
| `GET /v1/bank/full?grant=…&lang=he` | `examiner` בלבד | גוף `assets/bank/<lang>.json` כזרם (Content-Type JSON, `Cache-Control: no-store`, CORS) |
| `POST /v1/invalidate?grant=…&sessionCode=X` | **אישור בוחן חתום** (scope `examiner`, אותו grant של `bankGrant`; בלי אישור תקף → HTTP 403 `grant_invalid`, שום דבר לא נמחק ולא נכתב) · מוגבל: לכל היותר קריאה חוזרת אחת ל-2 שניות לסשן — אותו תקציב כמו סקר רגיל | `{"status":"ok"}` — מוחק את ה-snapshot של הסשן מהזיכרון ומה-Cache, כך שהסקר הבא קורא מהשרת מיד |
| `POST /v1/invalidate?grant=…&sessionCode=X&idNumber=Y&status=S[&extraMinutes&examMinutes&audio]` | **אישור בוחן חתום** (כנ"ל; הלוח שולח רק אחרי `ok` מהשרת) | **דחיפה נושאת החלטה (הודעה 21):** ה-Worker כותב את הסטטוס/הדקות/השמע לשורה של הנבחן ב-snapshot ומסמן אותו טרי — הסקר הבא של הנבחן (≤2 שנ׳) עונה מיד בלי קריאה לשרת; הקריאה שאחריה מאמתת. `{"status":"ok","patched":true|false}`; סטטוס לא מוכר → 400; דקות עד 600 |
| `GET /` | — | `{"status":"ok","service":"session-gateway","build":"…","bank":"<manifest.build>"}` |

## 12. סקר ארוך (long polling) — הבקשה של הנבחן נשארת פתוחה ב-Worker (21/09/2026 ערב, החלטת יוסי בשיחת הסקירה)

**למה:** בתוכנית החינמית של Cloudflare יש תקרה קשיחה של 100,000 בקשות ביום לכל ה-Workers של החשבון יחד (מעבר לה — שגיאה 1027 עד 00:00 UTC, ואז אין התחלת מבחן כי הבנק מוגש רק מה-Worker). עם סקר של 2–6 שנ' יום כבד (160 נבחנים) הגיע ל-~130 אלף. יוסי החליט: לא לשלם ולא להאט, אלא לעשות את זה נכון — והדרך הנכונה בחינם היא **לא** WebSocket/Durable Objects (מגבלת מעבד 10 ms לבקשה שמצטברת לאורך חיבור; טלפונים הורגים חיבור קבוע כשהמסך ננעל) אלא בקשה רגילה שמוחזקת פתוחה עד 25 שנ'.

### 12.1 ה-Worker (`/v1/poll`)

- `GET /v1/poll?kind=approval|status&sessionCode&idNumber&examineeToken[&wait=<1–25>&fp=<fp>]`.
- כל תשובה ללקוח ששלח `wait` או `fp` נושאת `fp` (חתימה קצרה, אטומה ללקוח, שמשתנה בדיוק כשהתשובה **לנבחן הזה** משתנה: `a:<approval>:<on|off>:<examMinutes|->` / `s:<examStatus>:<extraMinutes>` / `a:none` / `a:tok` / `x:up` …) ו-`held` (כמה ms הוחזקה). לקוח שלא שלח אף אחד מהם מקבל תשובה זהה בייט-לבייט לשרת (`tests/contracts.test.cjs`).
- **החזקה:** רק כש-`wait` ו-`fp` שניהם קיימים והתשובה הנוכחית זהה ל-`fp` של הלקוח — ה-Worker מחזיק, ועונה ברגע שהיא משתנה או בתום `wait` (אז אותה תשובה, אותו `fp`). `wait` לא תקין (0, שבר, מילה) = תשובה מיידית.
- **לעולם לא מוחזקים:** `upstream_unavailable`, `stale:true`, `examineeTokenError`, 400 — הלקוח חייב לקבל אותם מיד כדי להאט.
- **בזמן החזקה:** כל איטרציה (שינה של עד 1 שנ', או יקיצה) בודקת זיכרון → `caches.default` (טלאי שנכתב ב-isolate אחר) → upstream כשהעותק מעל `FRESH_MS`, **מאוחד** לכל הממתינים של הסשן (40 בקשות פתוחות = קריאה אחת ל-2 שנ' לגוגל, בדיוק כמו 40 סקרים רגילים). `patchSnapshot`, `dropSnapshot` וקריאה שהסתיימה מעירים את כל הממתינים של הסשן. שומר CPU: לכל היותר 26 איטרציות לבקשה (`HOLD_MAX_STEPS`); בקשה יכולה לחזור מוקדם עם `fp` זהה — הלקוח פשוט שואל שוב.
- `sleep` מוזרק ל-`createGateway` כדי שהבדיקות ירוצו על שעון מדומה. `handle._debug()` חושף ספירת ממתינים (חייבת להיות 0 אחרי שכל הבקשות נענו).

### 12.2 הלקוח (`shared/transport.js`, `examinee.html`)

- `createPollLoop`: תשובה מוצלחת עם `held > 0` מתזמנת את הבקשה הבאה אחרי `LONGPOLL_GAP_MS` (250 ms) במקום `baseMs`, ולא נחשבת "איטית" (אחרת מנגנון "שרת מדרדר" היה מאט את כולם). כשלים, backoff ו-degraded — ללא שינוי. `LONGPOLL_WAIT_SEC` 25, `LONGPOLL_TIMEOUT_MS` 40,000 (deadline לבקשה מוחזקת; `POLL_TIMEOUT_MS` 60 s נשאר התקרה).
- `examinee.html`: במסלול ה-gateway (אישור, סטטוס-במבחן, המתנה להחלטת פסילה) מצורפים `wait=25` ו-`fp` של התשובה האחרונה לאותו סוג; הבקשה הראשונה בכל שרשרת בלי `fp` → נענית מיד; `fp` נמחק במעבר מסלול (gateway↔ישיר), בסשן חדש ובכל התחלה מחדש של הלולאה. שתי בדיקות חד-פעמיות שמישהו מחכה להן על המסך (`onTimerExpired`, האימות אחרי רענון) נשלחות עם `noWait` — בלי `wait`/`fp`.
- **ספירת כשלים:** כשל רשת/timeout כשהדף לא גלוי, או תוך 2 שנ' אחרי שחזר להיות גלוי, הוא המכשיר (נעילת מסך) ולא ה-Worker — נענה כ-`{status:'error', code:'poll_interrupted'}`, הלולאה מאיטה צעד אחד, לא נספר ל"3 כשלים → ישיר 5 דק'", ולא מוצג. כשל אמיתי בזמן שהדף על המסך (5xx, לא-JSON, deadline) נספר כמו היום.
- **אין מסלול ישיר (יוסי, 21/09 ערב):** הנפילה לסקר ישיר מול Apps Script (3 כשלים → 5 דקות) הוסרה יחד עם `createFailover` — ה-Worker הוא הדרך היחידה. כשהוא לא עונה הדף מנסה שוב עם backoff (הסולם הקיים עד `maxMs`, ו-30–60 שנ' כש"השרת מדרדר") ומציג את שגיאת הסקר הרגילה אחרי 3 כשלים; סשן בלי `gateway.url` = שגיאת הגדרה שמוצגת מיד. `checkApproval`/`getExamStatus` פרשו מה-API באותו ערב (דף ישן מקבל `client_outdated`); הפונקציות נשארות כאמת-מידה לבדיקות החוזים. עמידות ל-Cloudflare-למטה נדחתה במפורש (TODO 4.3).

### 13.1 הקטנת הקובץ המודבק (פריט א)

הקובץ לגוגל מיוצר; המקור (`server/src/*.js`) נשאר מלא הערות. הבנייה (`tools/build_server.js`) עושה שני דברים חדשים:

1. **הסרת הערות במנתח אמיתי, לא ב-regex.** `tools/vendor/acorn.js` (acorn 8.18, MIT, מצורף לריפו כדי שבנייה בעץ נקי לא תדרוש `npm install`) מייצר את זרם האסימונים עם `onComment`; הבנייה חותכת את טווחי ההערות מהמקור ומוחקת שורות שנותרו ריקות. **אימות בתוך הבנייה:** ה-AST של הפלט (acorn, בלי שדות מיקום) חייב להיות זהה ל-AST של הקלט — אחרת הבנייה נכשלת. `node --check` על כל פלט כמו היום. נשמרות רק הערות שמכילות `©` (זכויות היוצרים) — וכותרת ה-GENERATED נוספת אחרי ההסרה.

### 13.2 לוח בוחן בלי טיימר (פריט ב) — `GET /v1/session/watch`

**הרעיון:** במקום שהלוח ישאל את גוגל כל 5 שנ׳ "מה חדש", הוא משאיר בקשה אחת פתוחה ב-Worker: "משהו השתנה בסשן?". ה-Worker כבר מחזיק את ה-snapshot של הסשן (השורות של `ממתינים`) בשביל הנבחנים, ומרענן אותו מגוגל כל ≤2 שנ׳ כל עוד מישהו מחכה עליו — לכן הצפייה של הבוחן **לא עולה לגוגל כלום נוסף**. ברגע שהטביעה של הסשן משתנה ה-Worker עונה, והלוח קורא `examinerDashboard` מיד (זו הקריאה היחידה לגוגל, והיא נעשית רק כשיש מה לראות).

**ה-Worker (`cloudflare-workers/session-gateway/worker.js`):**

| | |
|---|---|
| נתיב | `GET /v1/session/watch?grant=<אישור בוחן>&sessionCode=X[&wait=1..25&fp=<fp>]` |
| אימות | `verifyGrant(…, ['examiner'])` — בלי אישור תקף → HTTP 403 `grant_invalid`. `sessionCode` לא תקין → 400 |
| תשובה | `{"status":"ok","fp":"<fp>","held":<ms>,"rows":<n>,"at":<snapshot.at>}` (+ `"stale":true` כשהעותק ישן); אין snapshot בכלל → `{"status":"error","code":"upstream_unavailable","retryable":true,…,"fp":"x:up","held":0}` — לעולם לא מוחזק |
| הטביעה `fp` | `s:` + 12 הקסה ראשונות של SHA-256 על `rows.map(r => [id,status,audio,examMinutes,extraMinutes,warn,fin,ext,dq].join('|')).join(';')` בסדר השורות; שדה חסר (שרת ישן) = `''`. סשן בלי שורות → `s:none`. מחושבת פעם אחת לכל אובייקט snapshot (WeakMap) — ההחזקה לא מחשבת כלום מחדש |
| החזקה | כש-`wait` ו-`fp` קיימים והטביעה הנוכחית שווה ל-`fp` של הלקוח והעותק לא stale — אותה לולאה בדיוק כמו `/v1/poll` (HOLD_TICK_MS, HOLD_MAX_STEPS, HOLD_GRACE_MS, `waitForChange`, קריאה מאוחדת מגוגל על שעון FRESH_MS). **המימוש חייב להיות משותף:** `holdUntilChanged(session, look, clientFp, waitMs, ctx)` שמשמש את שני הנתיבים, לא עותק |
| מה מעיר | כל מה שמעיר היום: `patchSnapshot` (דחיפת בוחן), `dropSnapshot`, קריאה מגוגל שהסתיימה |
| `s:none` | מוחזק (ההרשמה הראשונה תיצור שורה ותעיר) |

**דף הבוחן (`examiner.html`):** מחליף את הלולאה הקבועה של 5/2 שנ׳ ב:

- `watchLoop = createPollLoop({ steady:true, baseMs: DASH_FALLBACK_MS (5000), tick: watchTick })` — `watchTick` שולח `…/v1/session/watch?grant&sessionCode&wait=25&fp=<lastWatchFp>` ב-`fetchJsonQuiet` עם deadline `LONGPOLL_TIMEOUT_MS` (40 שנ׳; ה-Worker לא הבקאנד — כשל שלו לא מסמן את גוגל "מדרדר"). תשובה `ok`: `watchHealthy = true`; אם `fp` שונה מהקודם → `lastWatchFp = fp` ו-`pollDashboard()` **מיד**. הבקשה הבאה יוצאת אחרי `LONGPOLL_GAP_MS` (250 ms) אחרי כל תשובה `ok` (מוחזקת או לא — ראו 13.4), ואחרי 5 שנ׳ אחרי כשל. 403 `grant_invalid` → `fetchBankGrant(true)` (אישור חדש) ושכחת ה-fp. אין אישור בוחן בכלל → הטיק נכשל מיד (fallback).
- **רענון ביטחון** (`setInterval` בדיקה כל 2.5 שנ׳): `pollDashboard()` אם עברו `DASH_SAFETY_MS` (60,000) מאז הבקשה האחרונה כש-watch בריא, או `DASH_FALLBACK_MS` (5,000) כשהוא לא. זה **לא** קצב רענון — זה רשת ביטחון לשינויים שלא עוברים ב-snapshot (תוצאה שתוקנה מדף אחר, השלמה אוטומטית של שורה תקועה) ולמצב שבו ה-Worker לא עונה (ואז הלוח מתנהג בדיוק כמו היום).
- `startDashboardPolling()`: `lastWatchFp = null`, `pollDashboard()` מיד, `watchLoop.start()`, הטיימר. `stopDashboardPolling()`: עוצר את שניהם. `pollDashboard()` רושם `lastDashboardAt` בזמן שליחת הבקשה, ונשאר "בקשה אחת בכל פעם" כמו היום. הרענון אחרי כל החלטה של הבוחן (`pollDashboard()` הישיר) והדחיפה (`nudgeGateway`) — ללא שינוי.
- **מוסר:** `DASH_POLL_SYNC_MS`, `DASH_SYNC_FAST_WINDOW_MS`, `dashSyncSince` (החלון של 2 שנ׳ "תוצאה בדרך") — הדחיפה מהמכשיר (13.5) מייתרת אותו.
- `visibilitychange` → `watchLoop.restartIfStuck()` (אייפד שהוקפא).

**מה זה נותן:** הרשמה → לוח: ~0.7 שנ׳ (הקריאה של ה-Worker מגוגל, שהסקר הראשון של הנבחן מכריח) + קריאת הלוח; הגשה → לוח: הדחיפה מהמכשיר (13.5) + קריאת הלוח. במקום עד 5 שנ׳ המתנה לטיק. כל קריאה לגוגל שנחסכת — לוח שקורא רק כשיש שינוי — היא גם פחות עומס בבוקר.

### 13.5 דחיפה מהמכשיר של הנבחן (הגשה, "סיימתי")

עד היום רק הבוחן דחף. הגשה ו"סיים במכשיר" הן כתיבות של הנבחן, ולוח הבוחן ראה אותן רק בקריאה הבאה של ה-Worker מגוגל (≤2 שנ׳) — ואז בטיק הבא של הלוח (≤5 שנ׳). עכשיו:

- **Worker:** `POST /v1/invalidate?sessionCode=X&idNumber=Y&examineeToken=T` **בלי `grant` ובלי `status`** — דחיפה של נבחן: ה-Worker מגבב את T ומשווה ל-`tokenHash` של השורה החדשה ביותר של Y ב-snapshot הנוכחי (זיכרון → cache `snap` → cache `stale`). תואם → `dropSnapshot` בתקציב `mayForceReread` (אותו תקציב כמו הדחיפה הריקה של הבוחן) → `{"status":"ok","dropped":true|false}`. אין snapshot לסשן → `{"status":"ok","dropped":false}` (אין מה למחוק ואין את מי להעיר). טוקן חסר/לא תואם → 403 `grant_invalid`. **לעולם לא patch** — רק הבוחן כותב לתוך מה שהנבחנים קוראים.
- **דף הנבחן:** `nudgeGatewayAfterWrite()` — אחרי `submitResult` שענה `ok` (מיד), ואחרי שליחת `markFinished` (2 שנ׳ אחרי — ה-beacon צריך לנחות בגוגל לפני שה-Worker קורא מחדש; זו לא המתנה למשהו שמישהו רואה, הבאנר הירוק הוא בונוס בזמן שהגשה איטית מסתנכרנת). `fetch(..., {method:'POST', keepalive:true, cache:'no-store'})`, fire-and-forget, אף פעם לא מציג שגיאה.

### 13.6 שרת — snapshot וביטול

### 14.1 (א) — הלוח מה-snapshot: מה עובר איפה

**שרת (`52_pending_status.js`, `handleSessionSnapshot`) — snapshot גרסה 2.** התשובה: `{ status:'ok', v:2, at, rows:[…], results:[…] }`.

**Worker (`worker.js`).**

- `fetchUpstream` שומר `v` (`Number(data.v)||1`) ו-`results` (מערך, או `[]`) בתוך ה-snapshot. `approvalAnswer`/`statusAnswer`/`evaluate` **לא משתנים** — שדות נוספים בשורה לא מגיעים לתשובת הנבחן (`contracts.test.cjs` נועל בייט-לבייט).
- **הטביעה `sfp`:** `rowsPart` כמו היום (`SESSION_FP_FIELDS`), ובנוסף כשיש תוצאות: `resultsPart = results.map(r => RESULT_FP_FIELDS.map(f => fpCell(r,f)).join('|')).join(';')` כש-`RESULT_FP_FIELDS` = **כל** שדות התוצאה בסדר קבוע (כולל `fabricated`). `sfp = 's:' + sha256(rowsPart + '#' + resultsPart).slice(0,12)` **רק כש-`results.length > 0`**; אין תוצאות / שרת ישן / מערך ריק → `'s:' + sha256(rowsPart)` — **זהה בייט-לבייט ל-r31**, כדי שפריסת ה-Worker (לפני הדבקת השרת) לא תזיז שום טביעה ולא תיצור flip-flop בין אייסולייטים (לקח 22/09, `SESSION_FP_ZEROABLE`). `rows.length === 0 && results.length === 0` → `s:none` כמו היום.
- **תשובת ה-watch:** `{ status:'ok', fp, held, rows:<מספר>, at [, stale:true] [, session:{ rows:[…], results:[…] }] }` — `session` **רק** כאשר (1) `snapshot.v >= 2`, (2) התשובה אינה `stale`, ו-(3) `fp !== clientFp` (או שאין `clientFp`). החזקה שפגה בלי שינוי עונה כמו היום (בלי `session`). `session.rows[i]` הוא עותק של השורה **בלי `tokenHash`**. `patchSnapshot` שומר `v`/`results` של העותק הקיים (הפאטץ׳ נוגע רק בשורה אחת).
- **CPU (TODO 0א.6):** `cacheWrite` מוסיף ל-Response המאוחסן כותרות `X-SFP: <sfp>` ו-`X-RAT: <rat>`; פונקציה חדשה `cacheFingerprint(kind, session, maxAgeMs)` קוראת **רק כותרות** (`match` בלי `json()`), מחזירה `{sfp, rat}` או `null` (מכבדת `maxAgeMs` מול `X-RAT`; עותק ישן בלי כותרות → `null` = "לא ידוע", ואז נופלים לקריאה המלאה כמו היום). ב-`lookAtNewest`, כשיש עותק בזיכרון והתצוגה ממנו שווה ל-`clientFp`: קודם `cacheFingerprint('snap')`; אם ה-`sfp` בכותרת שווה ל-`mine.sfp` — העותק במטמון הוא אותו snapshot, **אין פרסור** (מחזירים `fromMemory`); רק כשהוא שונה קוראים את הגוף. עותק שנקרא מהמטמון בלי שיש בזיכרון (`loadSnapshot`/`lookAtNewest`) **מאומץ לזיכרון** (`memory.set(session, {at: rat, snapshot})`) כדי שהטיק הבא ישווה כותרת בלבד. תוצאה: החזקה שקטה = טיק של `match` + השוואת מחרוזת, לא `JSON.parse` של 5–40 KB בכל שנייה. בדיקה: "watch מוחזק 25 שנ׳ ללא שינוי מפרסר את גוף המטמון לכל היותר פעם אחת" (מונים `json()` בכפיל המטמון, שצריך עכשיו גם `headers`).
- `BUILD = '2026-09-23'`. שורת היומן: גם `nr` (מספר התוצאות) ו-`sess:1` כשנשלח `session`.

**דף הבוחן (`examiner.html`).**

- `watchTick`: תשובה `ok` שנושאת `session` → `renderFromSession(data.session)` (גם כשזו התשובה הראשונה של השרשרת — נתונים הם נתונים; `watchPrimed` נשאר רק כדי לא לקרוא `examinerDashboard` על התשובה הראשונה). תשובה `ok` שהטביעה שלה השתנתה **בלי** `session` (Worker ישן, או `stale`) → `refreshDashboardSoon()` כמו היום. כלומר: **קריאת `examinerDashboard` על שינוי טביעה נשארת רק כנפילה לאחור.**
- `renderFromSession(session)`: בונה `pending`/`active` מ-`session.rows` **באותם כללים בדיוק** כמו `55_dashboard.js` (סטטוסים `waiting|approved` → pending, השורה האחרונה לכל ת.ז. מנצחת; `in_exam|disqualified` → active, `disqualified` (עם `dqPending:true`) מנצח `in_exam`, ובאותו סטטוס האחרונה מנצחת; פריט עם **אותם שמות שדות** כמו הלוח: `idNumber, name, phone, time, examStartTime, status, language, population, site, license, audioMode, timeExtension, dqCount, warnings, lastWarning, attemptsToday, hasExtendedScreen, extraMinutes, finishedOnDevice, todayExams, dqPending`); `completed` מ-`session.results` + `registrationTime` (מ-`rows`) + `wrongDetails` מ-`resultDetails` (מטמון בדף, ראו להלן; לא ידוע → `undefined`, **לא** `''`). ואז בדיוק מה ש-`pollDashboard` עושה עם תשובה טובה: `failedPolls = 0`, הסרת הבאנר, `window.__lastPending`, `updatePendingList/updateActiveList/updateCompletedList`. פונקציה אחת, `applyDashboardLists(pending, active, completed)`, משותפת לשני המסלולים — לא עותק.
- `resultDetails` — `{ '<idNumber>:<attempt>': wrongDetails }` שמתמלא מכל תשובת `examinerDashboard` (הפתיחה, רשת הביטחון, אחרי החלטות). **מה שצריך `wrongDetails`** (דו"ח לנבחן, דו"ח משותף, טבלת השגויות, שליחה מרוכזת — `grep wrongDetails`): לפני שהוא רץ, `ensureResultDetails()` — אם ב-`completedResults` יש פריט עם `wrongDetails === undefined` (ולא `fabricated`) → `pollDashboard()` ורק אז ממשיך (הרצה אחת בגוגל על לחיצה של הבוחן, לא על שעון). `''` הוא ערך ידוע (תוצאה בלי שגויות), לא "חסר".
- **מה לא משתנה:** הקריאה בפתיחה (`startDashboardPolling` → `pollDashboard()`), רשת הביטחון (60 שנ׳ כש-watch בריא / 5 שנ׳ כשלא, כולל אחרי קריאה שנכשלה), `pollDashboard()` הישיר אחרי כל החלטה (זו לחיצה של הבוחן, לא שעון; והיא גם מה שמביא `wrongDetails` של תוצאה שנוצרה מהחלטה — פסילה מאושרת, סיום כפוי), הדחיפה (`nudgeGateway`), `refreshDashboardSoon`, כל ה-`prev*` (צלילים). **חדש:** כל כתיבה של הדף ל-`תוצאות` שאינה עוברת ב-`examinerDecision` (סימון "נשלח", תיקון ציון, ביטול תוצאה — `grep` לפעולות ה-API שכותבות תוצאות) שולחת `nudgeGateway(null)` (drop) אחרי `ok`, כדי שה-`sent`/התיקון יגיעו ל-snapshot מיד ולא ב-20 שנ׳ ולא יהבהבו לאחור ברינדור הבא.
- **תאימות:** Worker ישן (בלי `session`) → הדף מתנהג בדיוק כמו r31.3c; שרת ישן (snapshot v1) → ה-Worker לא שולח `session` → כנ"ל.

### 14.2 (ב) — מסך המתנה מיידי, ההרשמה רצה ברקע

**דף הנבחן (`examinee.html`).** לחיצה על "הירשם" (אחרי `validateIdForm`):

1. **מיד:** `saveExamineeState('screenInstructions')` (עם `examineeData.regKey` שכבר נשמר היום, ו-`examineeData.registrationPending = true`), `showScreen('screenInstructions')` (שלב ההמתנה), `applyUITranslations()`, `startApprovalPolling()` — ה-Worker מחזיק `a:none` עד שהשורה מופיעה (§13.2 "No row yet IS held"), ולכן "ממתין"/"אושר" יופיעו בטלפון ברגע שה-Worker קורא את השורה — גם לפני שתשובת ההרשמה חזרה. שורת מצב חדשה מתחת ל-"ממתין לאישור הבוחן…": `#regStatus` — "שולח את ההרשמה לשרת…".
2. **ברקע — `registrationLoop`:** `apiGet(registerExaminee, …, regKey: registrationKeyFor(id))` עם deadline **`API_TIMEOUT_MS` (30 שנ׳)** — לא 60 (הניסיון החוזר לאותו `regKey` הוא חסין, וכל ניסיון הוא כרטיס הגרלה חדש במסירה של גוגל). תוצאות:
   - `ok` (עם או בלי `resumed`) → `examineeToken`, `registrationPending = false`, `saveExamineeState`, `nudgeGatewayAfterWrite()` (כמו היום), `#regStatus` = "נרשמת ✔ ממתין לאישור הבוחן", כפתור ההתחלה משתחרר (ראו 3).

   - סירוב מכוון (`status:'error'` שאינו "כבר רשום", אינו `retryable`, אינו `client_outdated`: סשן מלא, פסילה ממתינה, 'קוד סשן לא תקין'/'הסשן הסתיים'/'תוקף הסשן פג' (TODO 1.5)) → עוצרים את הסקר, מוחקים `registrationPending`, חוזרים ל-`screenIdForm` עם ההודעה ב-`#registerError` (כמו היום). `client_outdated` → `UPDATING_MESSAGE` שם.

   - כשהסקר עונה `waiting`/`approved` לפני שההרשמה ענתה — השורה כבר בגיליון: `#regStatus` = "ההרשמה הגיעה לבוחן ✔ מחכים לאישור ההרשמה מהשרת…" (הטוקן יגיע מהניסיון הבא, `resumed:true`).

## 15. r33 — מסלול גיבוי דרך גוגל לטלפון שלא מגיע ל-Worker, ותיקון פסילות השווא באייפון (23/09/2026 ערב, אישור יוסי "תתחיל א+ג"; KNOWN_ISSUES #38)

**מה ראינו ב-23/09 (לוג ה-Worker, `docs_private/incidents/2026-09-23/`):** לפחות 13 נבחנים בשלושה אתרים נרשמו דרך גוגל (השורה בגיליון, הבוחן אישר/איפס אותם עד 5 פעמים) אבל **אף בקשה שלהם לא הגיעה ל-Worker** — כל אישור ואיפוס נפלו לריק, והאתר הגדול עבר לבכתב. הדפוס לא ייחודי לאתר (קרה גם באתרים הקטנים), כמעט כל מי שכן הגיע התחבר ב-IPv6 (כתובת אישית לטלפון), ולפי יוסי ספארי (רגיל ופרטי) נכשל כשכרום באותו אייפון עבד. ההשערה המובילה: Cloudflare חוסמת חלק מהלקוחות ב-`workers.dev` לפני שה-Worker רץ (גל דיווחי 403/1010 מספטמבר 2026; לבעלים אין שליטה ואין לוג). לא הוכח; r33 לא תלוי בהוכחה. במקביל: שלושה אייפונים נפסלו 15–45 שנ׳ אחרי התחלה/חזרה (אחד שלוש פעמים) — "זוהה מסך מפוצל" על אייפון, שאין בו מסך מפוצל לספארי.

### 15.1 דף הנבחן — מסלול גוגל (`examinee.html`, "Google fallback")

- **מצב:** `gwMode` = `worker` (ברירת מחדל) / `google`. נכנסים ל-`google` רק כש: (1) **בדיקת הדלת** במסך הקוד נכשלה — `GET <gw>/` (תשובה מה-Worker בלבד, בלי גוגל) פעמיים בהפרש 1.5 שנ׳, ואז `fetch(<gw>/cdn-cgi/trace, {mode:'no-cors'})` רק לאבחון (`answered` = משהו ענה בכתובת — דף חסימה/אתגר; `none` = אין מסלול בכלל); (2) **3 כשלים רצופים** של סקר ה-Worker (`GW_FAILS_TO_FALLBACK`) שנספרים לפי `gatewayFailureCounts` — בקשה שהמכשיר הרג (מסך נעול, רקע, 2 שנ׳ אחרי חזרה) לא נספרת; **מ-r33.3 גם לא נספר timeout של בקשה מוחזקת** (ב-23/09 3.5–10% מהבקשות המוחזקות רצו 41–56 שנ׳ — ה-Worker מחכה לגוגל תקוע. אם היו נספרות, כל הכיתה הייתה עוברת לגוגל בדיוק בתקיעה). טלפון שלא מגיע ל-Worker נכשל מיד (רשת, HTTP, דף שאינו JSON), או ב-timeout של בדיקת הדלת, שם אין החזקה; תשובת JSON של ה-Worker (כולל `upstream_unavailable`) היא **הצלחה** ומאפסת את הרצף; (3) טעינת הבנק מה-Worker נכשלה ב-`network`/`timeout`/`nonjson`; (4) `?gw=google` בקישור (חזרות, וטלפון שידוע שנתקע) — בלי בדיקת דלת ובלי חזרה.
- **המסלול:** `pollRoute` → `googleRoute(kind)`: `approval` → `checkApproval`, `status` → `getExamStatus` (שתי הפעולות קיימות בשרת; ה-Worker נבנה לענות בדיוק כמותן). רווח מינימלי לכל סוג: **12 שנ׳** לאישור (משותף ללולאת האישור ולהמתנה להחלטת פסילה), **20 שנ׳** לסטטוס (משותף לסקר במבחן ולאישור ההגשה); `noWait` (אימות אחרי רענון, בדיקת הארכה בסוף הזמן) — מיידי. אין טביעה → אין re-arm; `nextDelay` של האישור מחזיר `max(paced, 12 s)`. כשלים בגוגל עוברים את `noteTransport` הרגיל (degraded → 30–60 שנ׳).
- **הבנק:** `loadExamTexts` — במצב `google` ישר ל-`bankRelay`; במצב `worker` קודם `QuestionBank.loadGrant`, ורק כשל **הגעה** (`network`/`timeout`/`nonjson`) עובר ל-`bankRelay` ומכניס למצב `google`; Worker שענה וסירב (403 grant, 503 bank) — השגיאה חוזרת כמו קודם (הממסר היה מסורב אותו דבר). התשובה נבלעת דרך `QuestionBank.ingestAnswer` — אותו קוד שבולע את תשובת ה-Worker.
- **חזרה ל-Worker:** אחרי דקה `GET <gw>/` שוב; כל דפיקה שנכשלה וכל נפילה קודמת בעמוד מכפילות את ההמתנה (1→2→4→5 דק׳ תקרה). הצליחה → `worker`, אפס רצף, דיווח `mode:'worker'`.
- **שמירה:** `sessionStorage['ext_gw_mode'] = {code, mode, n, at}` — רענון באותה לשונית (עד 3 שעות, אותו קוד סשן) נשאר ב-`google` בלי לבזבז שלושה סקרים כושלים.
- **דחיפות (`nudgeGatewayAfterWrite`)** לא נשלחות במצב `google` — ה-Worker לומד על השורות מהדחיפות של הבוחן ומקריאת הביטחון (45 שנ׳). **תוצאה לבוחן:** טלפון במצב גוגל יכול להופיע בלוח באיחור של עד ~45 שנ׳, והאישור מגיע אליו תוך ≤12 שנ׳.
- **על המסך:** `#gwStatus` (ירוק, 7 שפות, `gwFallback`): "📡 הטלפון לא מצליח להגיע לשרת המבחן, ולכן עבר אוטומטית לחיבור חלופי דרך Google… אין צורך לרענן". בכניסה למצב הבאנר האדום של כשלי ה-Worker נסגר ו-`approvalFailCount` מתאפס. נוסח הבאנר האדום כבר לא מציע "רענן את הדף".
- **אבחון לשרת (`gwDiag`, ≤300 תווי ASCII):** `v1|why=probe|forced|approval|status|bank|restored|late|e=<name:message>|t=<transport>|ms=…|trace=answered/none/timeout|n=…|ever=0/1|os=…|br=…|on=0/1`. לפני שיש שורה — נשלח עם `registerExaminee` (`gwDiag`); אחרי — `reportGateway` (POST no-cors, פעם אחת לכל טוקן; שוב עם `mode:'worker'` בחזרה).

### 15.2 שרת (`server/src`)

- **`bankRelay`** (exam, POST, טוקן נבחן, מגבלת קצב): מאמת את ה-grant בעצמו (חתימה, `s:'exam'`, `sub = session:id`, `exp`), `UrlFetchApp` ל-`GATEWAY_URL/v1/bank?grant=…` (ה-Worker לא בודק Origin — רק את ה-grant), מחזיר את גוף ה-Worker כמות שהוא + `relay:true`; כל כשל → `relay_failed` (retryable). **תלות:** גוגל → workers.dev חייב לעבוד — `testGatewayReachability()` בעורך אחרי ההדבקה.
- **`reportGateway`** (exam, POST, טוקן נבחן, מגבלת קצב): כותב רק את עמודה Q (`lastWarning`) = `📡 גיבוי גוגל…` / `📡 חזר ל-Worker`, לא נוגע במונה האזהרות (P), ורושם את `diag` בגיליון האבחון.
- **`registerExaminee`** + `gwDiag`: Q = `📡 גיבוי גוגל` כבר בשורה החדשה, והאבחון לגיליון.
- **`disqualify`** + `reason` (פסילה עצמית): Q = `פסילה: <reason>` — הבוחן רואה למה.
- `THEORY_API_BUILD = '2026-09-24-r33'`.

### 15.3 לוח הבוחן (`examiner.html`)

תג כחול קטן על שורה ש-Q שלה מתחיל ב-`📡` ("הטלפון עובד דרך Google").

### 15.4 אייפון — פסילות שווא (`examinee.html`)

`isIPhone()` = UA של iPhone/iPod, או Macintosh עם מגע ומסך צר מ-600 (אייפון ב"אתר שולחני"). באייפון: **לא** מפעילים את `startMobileSplitMonitor` (יחס שטח < 0.6 → פסילה אחרי 15 שנ׳) ו-`onSplitResize` לא פוסל (יחס 0.65). זום-אאוט (`visualViewport.scale` < המקורי) עדיין פוסל, והמקורי הוא `min(1, scale)` בתחילה/חזרה — התחלה בזמן זום-אין ואז חזרה ל-1.0 אינה "זום-אאוט". יציאה מספארי (`visibilitychange`) — כמו קודם. באנדרואיד ובאייפד הכל כמו קודם. כל פסילה עצמית נושאת `reason` (12 קודים: `hidden-final|hidden-10s|hidden-5s|fullscreen-exit|fullscreen-prompt|zoom-out|split-start|split-area|split-resize|blur-hidden-final|blur-hidden-10s|blur-hidden-5s`).

### 15.5 Service Worker של התרגול (`sw-student.js`)

כל הדפים רושמים SW באותו scope, ולכן טלפון שתרגל פוגש את דף המבחן תחת `sw-student.js` — שלקח **כל** GET חוצה-מקור (סקרי ה-Worker, `/v1/bank` — ושמר את הטקסטים במטמון עם ה-grant). עכשיו רק אותו מקור; ב-`activate` נמחק מהמטמון כל מה שנשמר ממקור אחר.

### 15.6 בדיקות
